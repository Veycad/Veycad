# Локальное ревью Sigma — 18 сентября 2026

Проверено текущее рабочее дерево, включая общие изменения кадрирования после ревизии 23. Реализация не менялась, сборки и видеорендеры не запускались. Выполнены чтение цепочки renderer → sampler → acceptance, проверка тестов, численные контрпримеры формулам и `git diff --check`. Это статическое ревью с вычислительными проверками, не новая GPU-приёмка.

Предмет ревью — стиль Sigma в приложении, не внешний скилл. Проверена цепочка MontageStyleCatalog → VeycadAutomaticEditor → VeycadEventPipeline → EventMatchingDirector → HighQualityFramePlan → MediaCodecSpeedRampRenderer → RenderedVisualSampler / RenderedMp4Acceptance / VeykadRenderInspector. Отдельный SKILL.md для этого не требуется.

## 1. P1 — композиция Sigma использует координаты исходника вместо экрана

`MediaCodecSpeedRampRenderer.kt:1212` присваивает `vScreenTexCoord=incoming`, где incoming уже содержит center-crop. Зеркальная композиция в строках 1503–1508 продолжает считать эти координаты экранными: её центры заданы как 0,25/0,75. Для горизонтального 1920×1080 в вертикальном 720×1280 crop.x=0,31640625, доступный диапазон x=0,341796875…0,658203125. Центры обнаруженного лица оказываются в output x≈−0,2901 и 1,2901, за границами кадра. Обычный центрированный узкий портрет в такой паре будет обрезан/потерян. Финальная сцена также строится из этих координат (1361), поэтому её геометрия зависит от aspect исходника. Текущие SourceFramingTest проверяют crop обычного изображения и маски, но не зеркальную сцену Sigma.

Исправление: строить композицию в output UV и отдельно переводить координаты выборки в source/crop UV; проверять пару и финал на landscape, square и portrait входах. Простая замена всех UV одним значением небезопасна: маски должны оставаться привязаны к исходнику.

## 2. P1 — QA изоляции финала проверяет другую маску, чем shader

`RenderedVisualSampler.kt:268–276` применяет к expectedStageMask только crop и ClipTransform. Shader Sigma дополнительно уменьшает и перемещает силуэт через `stageRaw=(vScreenTexCoord-vec2(.5,.48))/.72+vec2(.5,.5)` (`MediaCodecSpeedRampRenderer.kt:1361`). QA не воспроизводит это преобразование. `subjectStageBackgroundLuma` (730–742) исключает из проверки всю исходную большую фигуру, включая область, которая в готовом кадре уже должна быть фоном. Поэтому утечка/ореол вокруг уменьшенной фигуры может пройти. Для смещённых поз возможно и обратное: часть корректной фигуры будет посчитана фоном.

Численный контроль на сетке 48×72: исходная маска x=0,2…0,8, реальный силуэт уменьшен до 72%; яркость утечки в оставшейся полосе 0,3. QA по текущей маске возвращает фон 0,0, хотя реальная средняя яркость фона 0,085714. Увеличение яркости утечки не влияет на ошибочное нулевое значение QA. Это контрпример формуле, не измерение существующего MP4.

Исправление: воспроизвести точную композицию SUBJECT_STAGE в expected mask, включая масштаб/центр и границы. Добавить отрицательный контроль с утечкой именно в полосе между двумя силуэтами.

## 3. P2 — гейт двойной экспозиции не доказывает её наличие

`DecodedEffectSignature.kt:39–58` использует энергию и автокорреляцию горизонтальных градиентов только готового кадра. Контрольный обычный кадр с вертикальными полосами яркости 0,15/0,85 шириной два пикселя получает score=1,0 при пороге acceptance 0,28. Наложения в нём нет. Существующий тест `double_exposure_signature_requires_repeated_edge_energy` как раз использует полосы как положительный пример. Любая детальная текстура может поднять показатель; затемнение снижает его без исчезновения эффекта. Поэтому регулирование непрозрачности ради прохождения этого гейта не обеспечивает художественное улучшение.

Исправление: проверять появление второго пространственно смещённого источника относительно первичного кадра, использовать отрицательные примеры с текстурами и изменением экспозиции. До этого считать показатель диагностикой и не выдавать его за подтверждение двойной экспозиции.

## 4. P2 — зеркальная пара декодирует второй источник, который не использует

`MediaCodecSpeedRampRenderer.kt:253–295` считает любой MIRROR_SLICE двухисточниковым эффектом: выбирает второй декодер, выполняет seek/advanceTo, ожидает кадр и обновляет outgoing texture. Однако ветка Sigma (1500–1525) строит обе половины из `uIncoming` и `uMask`, возвращает результат и не использует `uOutgoing`. Второй поток нужен общей зеркальной ветке других стилей, но этой композиции Sigma не нужен.

Избыточность распространяется на план и приёмку: `HighQualityFramePlan.kt:112–130` подбирает вторичный момент и минимальное расстояние между источниками; `VeykadRenderInspector.kt:276–290` может отвергнуть такой эффект за близкие моменты, хотя они не влияют на картинку зеркальной пары. Кроме лишней работы, ненужный декодер остаётся дополнительной причиной отказа рендера.

Исправление: явно различать одноисточниковую пару Sigma и временное отражение. Убирать вторичное декодирование, подбор PTS и соответствующий QA-контракт согласованно. Для DOUBLE_EXPOSURE и общей ветки отражения сохранить второй источник. Экономия времени не измерена.

## Дополнительные места для упрощения

- `EventMatchingDirector.kt:44–49` всегда строит DYNAMIC, BALANCED и CINEMATIC. `VeycadAutomaticEditor.kt:152–154` оставляет запрошенный стиль только после этого. Для Sigma с выбранным DYNAMIC два плана лишние. Передавать выбранный вариант в director; все три сохранять только для автоматического выбора. Это лишнее планирование, а не три полных видеорендера: фильтрация уже находится до кодирования.
- `HighQualityFramePlan.kt:135–149` на каждом кадре повторяет 80-шаговое вычисление `integral(1f)`, постоянное для данного клипа и speed track. Знаменатель можно рассчитывать один раз на клип. Это низкоприоритетная оптимизация; без профилирования нельзя назвать её причиной долгих итераций.

## Что сейчас идёт не так

Описание эффекта разошлось между профилем, планом, shader и QA. Наиболее явный пример — зеркальная пара: изображение уже одноисточниковое, а инфраструктура продолжает требовать два источника. У финальной сцены shader и sampler используют разные силуэты. Проверка экспозиции оценивает текстуру вместо доказательства наложения. В результате техническое прохождение проверок не является надёжным сигналом художественного улучшения.

Выбор кадров тоже имеет ограничение: `EventMatchingDirector.kt:403–464` оценивает крупность по относительному размеру лица, а разнообразие — по повороту головы, масштабу и яркости. Это полезные признаки, но они не доказывают полный рост или смену сцены. Маленькое лицо само по себе не гарантирует нужную композицию референса. Доработка эффектов не устраняет это ограничение отбора и исходного материала.

Результаты ревизии 23 от 16 сентября не подтверждают текущее рабочее дерево с последующими общими изменениями кадрирования. По этому ревью нельзя честно вывести процент готовности или распределить потраченные четыре часа по причинам: текущие рендеры и профилирование не выполнялись.
