`quality_holdout_next.py` проверяет реальные файлы/хеши/прежние критерии, читает
локальные `.result` и связывает раскрытие с SHA байтов отчёта и исходника. Берёт
обе DUALITY-сцены и фактический render source; отказы также означают раскрытие.
Все файлы одного родителя выводятся вместе, включая транзитивные связи через
parent hash/source. Уже известный pilot никогда не становится holdout. Новые
результаты отсутствия экспозиции НЕ доказывают слепоту. Нужны проверка происхождения,
переизданий/дубликатов и подтверждение отсутствия другой настройки/просмотра.

Реальная повторная проверка кандидата: 10 невыведенных файлов, 9 заявленных
родительских групп; 8 файлов длительностью >=15с от 7 групп. Ошибок целостности0.
Это технические счётчики, не доказательство 9 независимых съёмок или качества
каждого стиля. Три незакрытых технических условия: длинный портрет, контровой свет,
подтверждённый VFR. Набор не запечатан, `corpus_ready=false`. Остались разные
камеры/контейнеры/частоты и другие условия, но человеческая проверка происхождения
и пригодности всё равно обязательна. Короткие Johnny/vidyo4 не закрывают длинный
портрет и не образуют автоматически осмысленную DUALITY-пару.

Кроме этих трёх условий, перед выпуском остаются: >=3 положительных родителя на
КАЖДЫЙ стиль, >=3 осмысленных DUALITY-пары с обеими перестановками, все обязательные
отрицательные случаи, собственные грамматики/музыка/лица/жесты/движение, успешные
декодированные MP4/AAC-проверки и реальная подписанная приёмка 1x/0.5x. Общая
техническая насыщенность корпуса не закрывает эту матрицу. Нужен также короткий
<6с отрицательный DUALITY-кандидат; известный отдельный кандидат ещё не включён.

Новая подготовка запускается только в НОВЫЙ путь, никогда не перезаписывает старый
manifest. Полноценный gate для этой версии:

```powershell
python tools/quality_holdout.py --manifest docs/quality/holdout-manifest-v2-candidate.json
```

Он закономерно возвращает ненулевой код до закрытия условий и новой фиксации.
`quality_holdout_next.py` может завершиться успешно при неполном покрытии: это
генератор candidate, не релизный gate. Его6 тестов проверяют вывод всего родителя,
транзитивные связи, неизменность исходного списка, byte-bound primary/secondary
источники, отказ malformed SHA и запрет sealed input. Полный набор71 Python
quality-тестов прошёл на этапе подготовки; после добавления pre-seal guard прошли
все73 теста. APK/директоры/пороговые критерии этим изменением не меняются.

Проверка/новая фиксация теперь по умолчанию используют v2-candidate, а не старый
список с раскрытыми источниками. Даже при явном указании старого списка новый
`make_seal` отказывает известным раскрытым источникам и всем связанным родителям.
Сканирование локальных результатов проводится ТОЛЬКО перед новой фиксацией:
`verify_seal` не отклоняет историческую фиксацию из-за её собственных первых
результатов, появившихся после sealing. Два дополнительных теста закрепляют
оба случая. Это обнаружение известных раскрытий, не гарантия отсутствия
неизвестной экспозиции. Человеческий/provenance контроль всё ещё необходим.

На реальных текущих файлах проверено: явная попытка новой фиксации старого
candidate v1 возвращает code2 с именами пяти раскрытых источников. Новый seal
не создан. Прежний candidate SHA не изменён. Отдельная повторная проверка v2
возвращает code1 именно по портрету/контровому/VFR/отсутствию фиксации, без
ошибок целостности. Эти отказы являются правильной работой протокола, не
положительной приёмкой видео/корпуса.73 quality-теста прошли после CLI-проверки.
Повторная `verify_seal` архивной v1 её собственным сохранённым кодом/корнем
вернула пустой список ошибок. Архив и его прежняя фиксация не изменены. Для
Windows-проверки через stdin явно использован UTF-8: прежняя попытка с нативной
кодировкой искажала Unicode-метаданные при передаче, не данные в архиве.
