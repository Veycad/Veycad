# Версии и локальные релизы Veykad

Проект использует Git только локально. Удалённый репозиторий не настроен, а
`push`, публикация и передача кода запрещены без прямой команды владельца
проекта.

## Источники правды

- `versionName` и `versionCode` находятся в `app/build.gradle.kts`;
- выпущенные версии перечисляются в корневом `CHANGELOG.md`;
- точное состояние выпущенной версии закрепляется annotated Git-тегом;
- имя тега равно `v<versionName>`, например `v0.2.0-rc.1`;
- версия без соответствующего тега считается разрабатываемой, а не выпущенной.

На момент принятия этого процесса в Gradle указаны `versionName = "0.1.0"` и
`versionCode = 1`, но тега `v0.1.0` нет. Поэтому это development baseline, а не
подтверждённый релиз.

## Семантическая версия

Veykad использует SemVer 2.0.0 в формате `MAJOR.MINOR.PATCH`:

- `MAJOR` — несовместимое изменение стабильного продуктового контракта;
- `MINOR` — новая обратно совместимая функциональность;
- `PATCH` — обратно совместимое исправление существующего поведения.

До `1.0.0` продуктовый контракт считается нестабильным:

- исправление без новой возможности повышает `PATCH`: `0.2.0` → `0.2.1`;
- новая функция, новый монтажный стиль или существенное изменение режиссуры
  повышает `MINOR`: `0.2.1` → `0.3.0`;
- несовместимое изменение в период `0.x` тоже повышает `MINOR` и обязательно
  описывается в changelog;
- `1.0.0` выпускается, когда основные пользовательские и экспортные контракты
  признаны стабильными.

После `1.0.0` любое несовместимое изменение повышает `MAJOR`, новая совместимая
функциональность — `MINOR`, а исправление — `PATCH`. При повышении `MAJOR`
обнуляются `MINOR` и `PATCH`; при повышении `MINOR` обнуляется `PATCH`.

Продуктовый контракт Veykad включает:

- основные пользовательские сценарии;
- поддерживаемые входные медиа;
- наблюдаемое поведение автоматического монтажа и монтажных стилей;
- формат и свойства экспортируемого MP4;
- совместимость сохраняемых проектов, когда постоянное хранение будет добавлено;
- минимально поддерживаемую версию Android.

Замена внутреннего алгоритма не является несовместимым изменением, если этот
контракт сохраняется.

## Предрелизные версии

Для незавершённых релизных линий используются стандартные суффиксы:

- `0.2.0-alpha.1` — функция ещё меняется и может быть неполной;
- `0.2.0-beta.1` — функция собрана, идёт настройка качества и исправление дефектов;
- `0.2.0-rc.1` — кандидат на релиз, новые функции в него не добавляются;
- `0.2.0` — принятая стабильная версия этой релизной линии.

Каждый следующий кандидат получает новый номер: `rc.1` → `rc.2`. Содержимое
уже отмеченного тега не изменяется.

## Android versionCode

`versionCode` — отдельный монотонно возрастающий целочисленный номер сборки. Он
не кодирует SemVer и увеличивается для каждого нового APK/AAB, который нужно
установить поверх или распространить как отдельный кандидат.

Пример:

| versionName | versionCode |
| --- | ---: |
| `0.1.0` | `1` |
| `0.2.0-alpha.1` | `2` |
| `0.2.0-beta.1` | `3` |
| `0.2.0-rc.1` | `4` |
| `0.2.0` | `5` |

Обычные локальные debug-сборки между релизными кандидатами не требуют смены
версии.

## Release checklist

1. Убедиться, что выбранный набор изменений образует самостоятельную версию.
2. Выбрать следующий `versionName` по правилам выше.
3. Увеличить `versionCode` в `app/build.gradle.kts`.
4. Перенести относящиеся к версии записи из `Unreleased` в раздел новой версии
   в `CHANGELOG.md`; указать дату в формате `YYYY-MM-DD`.
5. Закоммитить подготовку релиза отдельным коммитом `release: prepare <version>`.
6. Выполнить как минимум `./gradlew testDebugUnitTest lintDebug assembleDebug`.
7. Выполнить релевантный device-render, проверить экспортированный MP4 и
   зафиксировать проверенный сценарий или артефакт в документации.
8. Получить визуальную приёмку владельца для сборок, где меняется результат
   монтажа или рендера.
9. Проверить чистоту рабочего дерева и создать annotated тег:

   ```bash
   git tag -a v0.2.0 -m "Veykad 0.2.0"
   ```

10. Убедиться, что тег указывает на release-коммит и что `versionName` совпадает
    с именем тега без префикса `v`.

Если любая обязательная проверка не пройдена, тег не создаётся. Исправление
после уже созданного тега выпускается новым `PATCH` или новым prerelease-номером;
существующий тег не переносится.

## Ветки и коммиты

- `codex/<тема>` — экспериментальная или рабочая ветка;
- checkpoint-коммиты фиксируют проверяемые этапы, но не являются релизами;
- один коммит содержит одну проверяемую смысловую порцию работы;
- релиз определяется тегом, а не названием ветки и не самим фактом сборки APK.

Успешная версия может быть продолжена в той же рабочей ветке либо объединена с
основной линией отдельным решением. Создание тега не означает `push` или
публикацию.

## Что хранится в Git

- исходный код приложения и движка;
- unit-тесты и debug device-regression harness;
- документация, changelog и локальный реестр багов;
- Gradle wrapper и декларативная конфигурация сборки.

## Что не хранится в Git

- пользовательские исходники и результаты рендера;
- Golden MP4 — они остаются локальными в `app/src/testFixtures/golden-mp4/`;
- APK/AAB и каталоги `build`;
- device-логи, Render Inspector artifacts и кэши;
- `local.properties` и локальные параметры Android SDK.

MP4-артефакты остаются рядом с проектом для сравнения, но история Git хранит
только воспроизводящий их код и метаданные проверок.
