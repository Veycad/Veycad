# Работа через пул-реквесты

Изменения проекта готовим в отдельной ветке `codex/<краткое-название>` и
передаём на ревью через pull request. Один PR должен решать одну связную задачу.
Несвязанные изменения из рабочего каталога не включаем в PR автоматически.

1. Создайте ветку от актуальной основной ветки удалённого репозитория.
2. Внесите изменения и выполните подходящие проверки. Основной gate:
   `./gradlew clean baselineVerify` (Windows: `.\gradlew.bat clean baselineVerify`).
3. Отправьте ветку и откройте PR по шаблону. Если работа или приёмка ещё
   не завершены, откройте draft PR и перечислите оставшиеся шаги.
4. Проверьте diff и результаты CI для последнего коммита. Workflow
   `Android baseline` и `Android UI` запускаются на событии `pull_request`.
5. Сливайте только после явного одобрения владельца проекта и успешных
   обязательных проверок. После новых изменений нужно повторное ревью.

Для изменений монтажа успешного CI недостаточно: в PR укажите результаты
проверки экспортированного MP4 и состояние человеческой приёмки. Известные
ограничения должны оставаться видимыми в описании PR.

## Правила коммитов для всего проекта

Один коммит — одна связная задача, которую можно понять и откатить отдельно.
Сохраняйте завершённый результат после подходящих проверок; не копите несколько
независимых задач до конца дня. Код и необходимые для него тесты включайте
в один коммит. Количество коммитов и время между ними не являются целью.

Используем [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)
с таким заголовком:

```text
type(scope): краткое описание результата
```

Тип пишется строчными латинскими буквами, scope необязателен. Для scope
используйте короткое название области строчными латинскими буквами, цифрами
и дефисами: `render`, `audio`, `ui`, `analysis`, `storage`, `quality`, `tools`.
Описание может быть на русском или английском; оно должно объяснять изменение.

| Тип | Когда использовать |
| --- | --- |
| `feat` | Новая возможность |
| `fix` | Исправление ошибки |
| `refactor` | Изменение устройства кода без изменения поведения |
| `perf` | Улучшение производительности |
| `test` | Изменение только тестов |
| `docs` | Изменение документации |
| `style` | Форматирование кода без изменения поведения |
| `build` | Зависимости и сборка |
| `ci` | Автоматические проверки |
| `chore` | Прочее обслуживание проекта |
| `revert` | Отмена предыдущего изменения |

Примеры:

```text
fix(render): устранить рассинхронизацию звука при ускорении
feat(ui): добавить выбор стиля монтажа
docs: описать правила коммитов
chore(render): сохранить checkpoint настройки переходов
```

Для несовместимого изменения добавьте `!` перед двоеточием и объясните
последствия в теле сообщения. В теле сложного коммита после пустой строки
укажите причину изменения и важные ограничения. Фактические команды проверок
и результаты фиксируйте в PR; не заявляйте успешные проверки без запуска.

Перед каждым коммитом просмотрите `git diff --cached` и выполните
`git diff --cached --check`. Добавляйте только файлы или фрагменты своей задачи.
Секреты, локальные настройки, сборки и пользовательские видео в коммит не входят.
Не переписывайте старую или опубликованную историю ради нового формата.
Правила применяются к новым коммитам после введения этой политики.

Если нужно сохранить незавершённую работу, используйте заголовок
`chore(scope): сохранить checkpoint ...` и draft PR с оставшимися шагами
и известными проблемами. Сообщения `update`, `wip` или `fix` без описания
результата не подходят. Автоматические merge-коммиты Git сохраняют обычный
заголовок; итоговый squash-коммит должен соответствовать нашему формату.
Для `git revert` измените заголовок на `revert: ...` и сохраните ссылку
на отменённый коммит в теле сообщения.

### Локальная проверка сообщения

В проект включены `.githooks/commit-msg` и шаблон `.gitmessage`. В каждом новом
клоне выполните из корня репозитория:

```shell
git config --local core.hooksPath .githooks
git config --local commit.template .gitmessage
```

На Linux/macOS также выполните `chmod +x .githooks/commit-msg`, если инструмент
копирования не сохранил исполняемый бит. Git for Windows запускает hook
через поставляемый с Git shell; Node.js и Python для этой проверки не нужны.
Если в клоне уже настроены собственные hooks, сначала объедините их с этим hook.

Hook отклоняет неверный формат заголовка при локальном `git commit`.
Его можно обойти через `--no-verify`; коммиты через GitHub или API этот hook
не запускают. Поэтому содержание и сообщения коммитов также проверяются в PR.
Hook не подтверждает корректность кода и не заменяет проверки проекта.

## Настройка удалённого репозитория

Удалённый репозиторий: https://github.com/rexarmakedonskij-hue/Veycad.
Репозиторий остаётся приватным. На текущем тарифе GitHub не применяет защиту
веток к этому репозиторию; владелец выбрал PR, проверки и ручное слияние.
Шаблон и этот документ задают порядок работы, но технически не блокируют
прямой push или слияние с неуспешными проверками.

Перед ручным слиянием проверьте успешные jobs `baseline` и `ui` для последнего
коммита, разрешение обсуждений и явное решение владельца о слиянии.
PR, опубликованный от аккаунта владельца, нельзя одобрить через собственный
GitHub Approve: для обязательного GitHub-ревью нужен другой участник.

Если в будущем тариф позволит применять защиту приватных веток, можно включить
обязательный PR, оба status check, актуальность ветки относительно `main`,
разрешение обсуждений и запрет обхода правил. Обязательное внешнее одобрение
включайте только при наличии отдельного ревьюера.
